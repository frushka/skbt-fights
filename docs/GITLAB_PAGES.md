# Деплой «Пульса зала» на GitLab Pages

Всё уже настроено: в репозитории лежат `.gitlab-ci.yml`, `vite.config.pages.ts` и скрипт
`build:pages` в `package.json`. Ниже — что с этим делать и как проверять.

## 0. Что важно понимать про этот проект

GitLab Pages раздаёт **только статические файлы**: PHP, Node-сервер, SSR там запустить негде.
А проект собран на TanStack Start — это SSR-фреймворк, обычная команда `bun run build` делает
серверный бандл под Cloudflare Workers (`.output/`), который Pages не запустит.

Поэтому для Pages сделана **отдельная статическая сборка**:

|           | Lovable / Cloudflare    | GitLab Pages                    |
| --------- | ----------------------- | ------------------------------- |
| Конфиг    | `vite.config.ts`        | `vite.config.pages.ts`          |
| Команда   | `bun run build`         | `bun run build:pages`           |
| Результат | `.output/` (SSR-воркер) | `dist/client/` (чистая статика) |

Существующий деплой на `skbt-fights.lovable.app` при этом не меняется — файлы независимы.

Приложение целиком клиентское — серверных функций у него нет, поэтому SSR ему не нужен и в
статике оно работает полноценно. Обмен значениями идёт по WebSocket с отдельным сервером
(`server/README.md`), который живёт своей жизнью и к публикации сайта отношения не имеет.

## 1. Пошаговая настройка

### 1.1. Перенести код в GitLab

Проект живёт в GitHub, поэтому нужен репозиторий на стороне GitLab. Два варианта:

**Вариант А — импорт (проще).** GitLab → **New project** → **Import project** → **GitHub**,
авторизоваться и выбрать `frushka/skbt-fights`. Импортируется вся история.

**Вариант Б — вторым remote.** Создать пустой проект в GitLab и запушить туда:

```sh
git remote add gitlab https://gitlab.com/<namespace>/skbt-fights.git
git push -u gitlab main
```

Импорт — разовая копия, живой связи между сервисами он не создаёт. Работа при этом идёт в
GitHub (туда же коммитит Lovable), а сайт собирается из GitLab, поэтому изменения нужно
доставлять.

### 1.2. Зеркалирование GitHub → GitLab

Автоматическое подтягивание на стороне GitLab (pull mirroring) доступно только на платных
тарифах, поэтому синхронизацию делает GitHub Actions — `.github/workflows/mirror-to-gitlab.yml`.
При каждом изменении `main` он пушит его в GitLab, а тот запускает пайплайн и обновляет сайт.

Что нужно один раз настроить:

1. **GitLab** → аватар → **Edit profile** → **Access tokens** → **Generate token** →
   **Personal access token**. Имя любое, срок — подлиннее, галочка ровно одна:
   **`write_repository`**. Значение токена показывается один раз, скопируйте сразу.
2. **GitHub** → репозиторий → **Settings** → **Secrets and variables** → **Actions** →
   **New repository secret**. Имя: `GITLAB_TOKEN`, значение: скопированный токен.

Адрес целевого репозитория зашит в workflow — при переезде правится там.

Запустить зеркалирование вручную можно во вкладке **Actions** → workflow **Mirror to GitLab** →
**Run workflow**.

### 1.3. Включить уникальный домен

**Settings → Pages → Use unique domain** (галочка включена по умолчанию для новых проектов).

Это не косметика, а требование архитектуры: сайт должен лежать **в корне домена**.
На дашборде ссылка для QR-кода строится как `window.location.origin + "/vote/" + roomId`
(`src/routes/dashboard.$roomId.tsx`), и роутер собран без `basepath`. Если сайт открыть
по адресу вида `https://<namespace>.gitlab.io/skbt-fights/`, то ассеты и QR-ссылка поедут.

С уникальным доменом адрес будет вида `https://skbt-fights-a1b2c3.gitlab.io/`.

### 1.4. Проверить, что Pages вообще включены

**Settings → General → Visibility, project features, permissions → Pages** — переключатель должен
быть активен. Там же выбирается, кто видит сайт (Everyone / только участники проекта).

### 1.5. Переменные окружения

**Обязательно.** В **Settings → CI/CD → Variables → Add variable** задайте адрес сервера
реального времени (галочку _Protect variable_ снять):

| Key                 | Value                  |
| ------------------- | ---------------------- |
| `VITE_REALTIME_URL` | `wss://<ваш-домен>/ws` |

Без неё сайт соберётся, но покажет «Сервер не настроен» вместо ползунка — это намеренно,
чтобы недостающая настройка не выглядела как поломка. Развёртывание самого сервера описано в
`server/README.md`.

Переменная подставляется **на этапе сборки**: изменили — запустите пайплайн заново, у уже
опубликованного сайта её не поменять.

Ключи Supabase (`VITE_SUPABASE_*`) остались в закоммиченном `.env` от прежней архитектуры;
на передачу данных они больше не влияют.

### 1.6. Запустить деплой

Просто запушьте в основную ветку — пайплайн стартует сам:

```sh
git push origin main
```

## 2. Разбор `.gitlab-ci.yml`

```yaml
image: oven/bun:1
```

Докер-образ для всех job'ов. В проекте `bun.lock` и `bunfig.toml`, значит и ставить зависимости
надо bun'ом — иначе лок бесполезен.

```yaml
stages:
  - deploy
```

Список стадий пайплайна. Стадия здесь одна: собрали и сразу опубликовали.

```yaml
cache:
  key:
    files:
      - bun.lock
  paths:
    - node_modules/
```

Кэш зависимостей между пайплайнами. Ключ считается от содержимого `bun.lock`: лок изменился —
ключ другой — кэш перестраивается. Так не приходится качать 418 пакетов на каждый коммит.

```yaml
pages:
  stage: deploy
```

**Ключевой момент.** GitLab считает деплоем Pages job с именем ровно `pages`. Переименуете —
сайт не опубликуется, пайплайн при этом останется зелёным.

```yaml
script:
  - sed -i 's#https://europe-west1-npm\.pkg\.dev/lovable-core-prod/sandbox-npm-cache/#https://registry.npmjs.org/#g' bun.lock
```

Девять пакетов (`@supabase/*`, `qrcode.react` и их зависимости) запинены в локе на приватное
npm-зеркало Lovable. Снаружи их песочницы оно отдаёт **403**, и установка падает. Пути внутри
зеркала совпадают с путями npmjs, поэтому меняется только хост — версии и integrity-хеши те же,
ставятся ровно те же пакеты. Правка живёт внутри job'а и в репозиторий не попадает.

```yaml
- bun install --frozen-lockfile
```

Установка строго по локу: если `package.json` разошёлся с `bun.lock`, job упадёт, а не соберёт
втихую другие версии.

```yaml
- bun run build:pages
```

Статическая сборка (`vite build --config vite.config.pages.ts`). На выходе `dist/client`:
ассеты, `favicon.ico`, `robots.txt` и пререндеренная оболочка `_shell.html`.

```yaml
- rm -rf public
- mv dist/client public
```

GitLab Pages публикует папку `public`. В репозитории `public/` уже занята исходными статик-файлами,
но Vite при сборке копирует их внутрь `dist/client`, так что ничего не теряется.

```yaml
- cp public/_shell.html public/index.html
```

В SPA-режиме TanStack Start пререндерит оболочку приложения в `_shell.html`. Главной страницей
сайта должен быть `index.html` — копируем.

```yaml
- printf '/*  /index.html  200\n' > public/_redirects
```

SPA-фолбэк. Файлов `/vote/abcd12` и `/dashboard/abcd12` на диске не существует — это клиентские
маршруты. Правило говорит Pages: на любой неизвестный путь отдай `index.html` **со статусом 200**
(не редиректом), дальше роутер разберётся сам. Файл обязан лежать в корне опубликованной папки.

```yaml
- cp public/_shell.html public/404.html
```

Подстраховка. Если `_redirects` по какой-то причине не сработает, GitLab отдаст `404.html` —
приложение всё равно загрузится и покажет нужный маршрут.

```yaml
artifacts:
  paths:
    - public
```

Артефакт — то, что job передаёт наружу. Pages забирает сайт именно отсюда: нет артефакта `public`
— нет публикации.

```yaml
rules:
  - if: $CI_COMMIT_BRANCH == $CI_DEFAULT_BRANCH
```

Job запускается только для основной ветки проекта (`main` или `master` — что настроено в
**Settings → Repository → Branch defaults**). Пуши в feature-ветки и MR'ы прод не перезаписывают.

## 3. Настройка конфигурации фреймворка

Всё уже в `vite.config.pages.ts`, но вот что там происходит и зачем:

```ts
export default defineConfig({
  nitro: false,
  vite: { server: { host: "127.0.0.1" } },
  tanstackStart: {
    server: { entry: "server" },
    spa: { enabled: true },
  },
});
```

- **`nitro: false`** — не собирать серверный бандл. По умолчанию обёртка Lovable гонит сборку
  через Nitro с пресетом Cloudflare; для Pages сервер не нужен и только мешает.
- **`spa: { enabled: true }`** — SSR выключен, TanStack Start один раз пререндерит оболочку в
  `dist/client/_shell.html`, дальше всё работает на клиенте. Именно это превращает SSR-приложение
  в статический сайт.
- **`vite.server.host: "127.0.0.1"`** — обёртка Lovable по умолчанию слушает на `"::"` (IPv6).
  Пререндер поднимает локальный сервер, и в CI-контейнере без IPv6 сборка падает с
  `listen EAFNOSUPPORT :: `. Явный IPv4-хост убирает эту зависимость от окружения.
- **`server: { entry: "server" }`** — повторяет настройку из основного конфига (SSR-обёртка
  `src/server.ts` с обработкой ошибок).

**Про `base`.** Он не задан намеренно: сайт публикуется в корне уникального домена, ассеты
запрашиваются как `/assets/...`. Если когда-нибудь понадобится подпапка `/skbt-fights/`,
одного `base` не хватит — нужно будет ещё задать `basepath` роутеру в `src/router.tsx` и
переписать генерацию QR-ссылки в `src/routes/dashboard.$roomId.tsx`.

Собрать статику локально (полностью повторяет то, что делает CI):

```sh
bun install
bun run build:pages
npx serve dist/client     # или любой статический сервер
```

## 4. Как проверить, что деплой прошёл

1. **Пайплайн.** Слева **Build → Pipelines**: последний пайплайн для основной ветки должен быть
   зелёным, внутри — job `pages` со статусом _passed_. В логе job'а в конце будет строка про
   загрузку артефакта `public`.
2. **Отдельный job публикации.** После `pages` GitLab сам запускает служебный job
   `pages:deploy` — он и раскладывает сайт.
3. **URL.** Слева **Deploy → Pages** — там написан адрес сайта
   (`https://skbt-fights-<hash>.gitlab.io/`). Там же переключатель unique domain и настройка
   своего домена.
4. **Проверка руками:**
   - открыть корень — должна быть страница «Настроение аудитории в прямом эфире» с кнопкой
     «Создать комнату»;
   - нажать кнопку — попадаете на `/dashboard/<код>`, виден QR и «Количество участников»;
   - **отдельно проверить прямой заход**: скопировать `https://.../vote/<код>` в новую вкладку.
     Если открылось — SPA-фолбэк работает (это главное, что ломается на статических хостингах);
   - открыть `/vote/<код>` с телефона, подвигать слайдер — на дашборде столбик должен реагировать
     мгновенно, а счётчик участников вырасти.

## 5. Возможные ошибки и решения

**Job `pages` не запустился, пайплайн зелёный**
Правило `rules` пропускает только основную ветку. Проверьте, что пушите в ветку по умолчанию
(**Settings → Repository → Branch defaults**), и что job называется именно `pages`.

**`error: GET https://europe-west1-npm.pkg.dev/... 403`**
Не отработал шаг с `sed` (или его убрали из конфига). Приватное зеркало Lovable недоступно
снаружи их песочницы — строка подмены хоста в `bun.lock` обязательна.

**`bun install --frozen-lockfile` падает с рассинхроном**
`package.json` изменили, а `bun.lock` не пересобрали. Локально: `bun install`, затем закоммитить
обновлённый `bun.lock`.

**Сборка виснет на `Port ... is in use, trying another one...` или падает с `listen EAFNOSUPPORT ::`**
В окружении нет IPv6, а пререндер поднимает сервер на `::`. Лечится строкой
`vite: { server: { host: "127.0.0.1" } }` в `vite.config.pages.ts` — она уже там.

**404 при прямом заходе на `/vote/<код>`, но с главной всё работает**
Нет SPA-фолбэка. Проверьте, что в артефакте в корне `public/` лежат `_redirects`
(с правилом `/*  /index.html  200`) и `404.html`.

**Белый экран, в консоли 404 на `/assets/*.js`**
Сайт открыт по подпути (`https://<namespace>.gitlab.io/skbt-fights/`) вместо уникального домена.
Включите **Settings → Pages → Use unique domain** либо привяжите свой домен.

**Пайплайн зелёный, но по URL пусто или 404**
Первая публикация Pages распространяется не мгновенно — до ~30 минут. Проверьте, что раздел
**Deploy → Pages** показывает адрес, и что Pages включены в **Settings → General**.

**На месте ползунка написано «Сервер не настроен»**
Не задана `VITE_REALTIME_URL` (см. 1.5) — либо задана, но пайплайн после этого не перезапускали.
Переменная подставляется на этапе сборки, у опубликованного сайта её не поменять.

**Экран висит на «Подключение…» или «Переподключение…»**
Сайт не достучался до сервера реального времени. По порядку: `curl https://<домен>/health`
должен вернуть `ok`; `systemctl status pulse` на VPS — что служба жива; в значении переменной
должна быть схема `wss://` и путь `/ws` на конце. Браузер не пустит `ws://` со страницы,
открытой по `https`, — сертификат на домене сервера обязателен.

**Числа доходят до дашборда, а потом замирают, при этом всё «Подключено»**
Так выглядит не отказ сервера, а фильтрация трафика по пути: соединение формально живо,
данные уже не идут. Ровно из-за этого проект и ушёл с Supabase — подробности в
`server/README.md`. Если симптом вернулся, проверьте, что сервер стоит на хостинге внутри
страны и что зрители идут к нему напрямую, без промежуточных прокси.

**QR ведёт не туда**
Ссылка строится от `window.location.origin`. Это корректно только когда сайт лежит в корне
домена — см. п. 1.3.

**Сайт не обновился после пуша в GitHub**
Pages собираются из репозитория GitLab. Если зеркалирование не настроено, пуш в GitHub сам по
себе пайплайн не запускает — нужно пушить и в GitLab (см. 1.2).
