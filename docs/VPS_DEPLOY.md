# Сайт и сервер реального времени на одном VPS

Всё приложение живёт на одной машине: Caddy раздаёт статику и проксирует WebSocket, сборку
доставляет GitHub Actions. GitLab в схеме не участвует.

```
GitHub (push в main) → Actions: сборка → rsync по SSH → /var/www/pulse на VPS → Caddy
```

## Почему так

Изначально статику раздавал GitLab Pages, а VPS появился отдельно — под сервер реального
времени, потому что российские провайдеры глушат трансграничное соединение с `supabase.co`
(подробности в `server/README.md`). Держать два хостинга ради нескольких мегабайт статики
незачем: Caddy уже стоял на сервере и умеет отдавать файлы.

Что это дало: один домен вместо двух, короткая ссылка в QR-коде, и на четыре звена меньше в
цепочке доставки — не стало зеркалирования в GitLab, его пайплайна и CI-переменной.

Чем платим: всё держится на одной машине. Ляжет она — ляжет и сайт, и голосование сразу.
GitLab Pages в этом смысле надёжнее, там сеть доставки с резервированием.

## Что где лежит

|                          |                                                                    |
| ------------------------ | ------------------------------------------------------------------ |
| Статика сайта            | `/var/www/pulse`                                                   |
| Сервер реального времени | `/opt/pulse/realtime.js`, служба `pulse`, слушает `127.0.0.1:8787` |
| Конфигурация веб-сервера | `/etc/caddy/Caddyfile`                                             |
| Выкатка                  | `.github/workflows/deploy-to-vps.yml`                              |

## Настройка сервера

Предполагается, что сервер реального времени уже развёрнут по `server/README.md`.

**1. Каталог для сайта и rsync:**

```sh
mkdir -p /var/www/pulse
apt install -y rsync
```

**2. Caddyfile:**

```caddy
skbt-fights.ru, www.skbt-fights.ru {
	handle /ws* {
		reverse_proxy 127.0.0.1:8787
	}
	handle {
		root * /var/www/pulse
		try_files {path} /index.html
		file_server
	}
}

rt.skbt-fights.ru {
	reverse_proxy 127.0.0.1:8787
}
```

Разбор:

- `handle /ws*` — всё, что начинается с `/ws`, уходит на сервер реального времени. Остальное
  отдаётся файлами. Порядок блоков не важен, Caddy выбирает по совпадению пути.
- `try_files {path} /index.html` — **ключевая строка**. Файлов `/vote/abcd12` и
  `/dashboard/abcd12` на диске нет, это клиентские маршруты. Без этой строки прямой заход по
  ссылке из QR-кода вернул бы 404.
- Блок `rt.skbt-fights.ru` остался с прежней схемы: приложение обращается к серверу по этому
  адресу. Его можно убрать, если переключить `VITE_REALTIME_URL` в workflow на
  `wss://skbt-fights.ru/ws` — тогда всё пойдёт через основной домен.

Применить: `systemctl reload caddy`.

**3. DNS.** A-записи `@`, `www` и `rt` должны указывать на IP сервера. У reg.ru проверьте, что
для корневой записи выключена «парковка домена» — иначе она перебивает вашу запись и домен
продолжает вести на заглушку регистратора.

## Ключ для выкатки

GitHub заходит на сервер отдельным ключом.

На своём компьютере:

```sh
ssh-keygen -t ed25519 -f ~/.ssh/pulse_deploy -C "github-deploy"
```

Публичную половину (`~/.ssh/pulse_deploy.pub`) — в `/root/.ssh/authorized_keys` на сервере.
Приватную (`~/.ssh/pulse_deploy`, целиком, вместе со строками `BEGIN`/`END`) — в
**Settings → Secrets and variables → Actions** под именем `VPS_SSH_KEY`.

Выкатка ходит под `root`. Для личного проекта приемлемо; строже — завести отдельного
пользователя с правом записи только в `/var/www/pulse`.

## Как выкатывается

Автоматически при пуше в `main`. Вручную — **Actions → Deploy to VPS → Run workflow**.

Шаги: установка зависимостей, `bun run build:pages`, копирование `_shell.html` в `index.html`,
`rsync --delete` в `/var/www/pulse`, проверка что файлы на месте.

Два места, которые выглядят странно, но нужны:

- **Подмена npm-зеркала.** Девять пакетов в `bun.lock` запинены на приватное зеркало Lovable,
  которое снаружи их песочницы отдаёт 403. Пути совпадают с npmjs, поэтому меняется только хост.
- **`rsync --delete`.** Имена ассетов содержат хеш содержимого, поэтому без очистки каталог рос
  бы с каждой выкаткой.

Адрес сервера и путь заданы в `env` в начале workflow — при переезде правятся там.

## Проверка

```sh
curl https://skbt-fights.ru/health   # ok — сервер реального времени жив
```

В браузере: главная, кнопка «Создать комнату», затем **скопировать ссылку `/vote/<код>` в новую
вкладку** — это проверяет `try_files`, то есть именно ту часть, что ломается на статических
хостингах.

Живая проверка: дашборд на компьютере, телефон **без VPN**, ползунок до +100 и удержать.
Значение должно дойти до края и вернуться к нулю за пять секунд, надпись — остаться
«Подключено».

## Типовые отказы

**Actions падает на `Секрет VPS_SSH_KEY не задан`**
Секрет не добавлен или назван иначе.

**`Permission denied (publickey)`**
Публичная половина не попала в `/root/.ssh/authorized_keys`, либо у файла неверные права:
`chmod 600 /root/.ssh/authorized_keys`.

**Сайт отдаёт 404 на `/vote/<код>`, главная при этом работает**
В Caddyfile потерялась строка `try_files {path} /index.html`.

**Открывается заглушка регистратора вместо сайта**
DNS ещё не переключён или включена парковка домена. Проверьте: `nslookup skbt-fights.ru`.

**Страница пишет «Сервер не настроен»**
В сборку не попала `VITE_REALTIME_URL`. Значение задаётся в `env` workflow; переменная
подставляется на этапе сборки, у выложенного сайта её не поменять — нужна новая выкатка.

**Экран висит на «Переподключение…»**
Сайт не достучался до сервера реального времени. По порядку: `systemctl status pulse`,
`curl https://rt.skbt-fights.ru/health`, и проверить схему `wss://` с путём `/ws` в значении
переменной.

## Обслуживание

```sh
systemctl status pulse caddy    # состояние служб
journalctl -u pulse -f          # логи сервера реального времени
journalctl -u caddy -f          # логи веб-сервера, в том числе выпуск сертификатов
```

Сертификаты Caddy продлевает сам. Ключ выкатки бессрочный — если он скомпрометирован, удалите
строку из `authorized_keys` и заведите новый.
